# Direction and structure

Start with the requested job, audience, real content, relevant states, and the existing
visual authority. Separate an established system, a new surface within that system, and an
authorized replacement. Reuse approved decisions; ask only about a material unresolved choice.
For a standalone design interview, use [grilling](../../grilling/SKILL.md) without repeating it.

For a new surface, identify the primary action or reading sequence before choosing decoration.
Compare a small number of structurally distinct approaches when the choice matters: explain
how each changes hierarchy, interaction, density, and implementation. Recommend one using the
user's purpose and constraints. A color swap on the same layout is not a distinct concept.
If direction is already settled, build from it without another approval round.

In Operate surfaces, favor predictable navigation, clear current state, scanable data, honest
feedback, and recovery. Preserve platform conventions and frequent-user efficiency. In Read
surfaces, organize for comprehension with headings, readable measure, and useful navigation.
Persuade surfaces need a truthful argument and an obvious next action; Experience surfaces
should let the actual work occupy the first view. Theme and density come from the use scene.

`shape` returns the smallest useful brief: job and audience, outcome and proof, selected
structure, scope, content ranges and states, interaction and responsive intent, constraints,
and open decisions. It stops before code or persisted design artifacts unless the user also
requested those outputs. Native Plan and Specs retain their own approval and handoff rules.

`init` captures durable product facts only when asked: purpose, audience, operating context,
capabilities, voice, constraints, and evidence. `document` records the observed visual system:
tokens, typography, spacing, components, states, and intentional exceptions. Update the
project's existing authority rather than introducing competing files. When PRODUCT.md or
DESIGN.md is the chosen location, distinguish observed facts from proposals and do not erase
unrelated content. PKStack project knowledge follows [okf](../../okf/SKILL.md); native design
instructions remain in their discovery location and link to shared facts rather than copying
the Wiki. A narrow refinement does not require initialization or documentation first.

Real imagery and fonts must fit the intended design and their usage rights. Use supplied or
already approved assets and project dependencies. Identify any missing asset honestly; do not
download fonts, purchase imagery, invoke a paid generator, or alter global tooling as an
implicit prerequisite. A mockup is a design reference, not proof of working interaction.
